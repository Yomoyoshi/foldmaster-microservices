1. Бизнес-требования (BRD)


	Цель документа: 
		Зафиксировать стратегические цели компании, которые должны быть достигнуты с помощью разрабатываемого сайта. 
		Этот документ — контракт между аналитиком и владельцем бизнеса.

	Название проекта: 
		Прототип интернет-магазина складной мебели
	Версия: 
		1.0
	Статус: 
		Согласован

1.1. Бизнес-контекст и проблема

	На данный момент компания продаёт складную мебель только через маркетплейсы.

	Проблемы: 
		высокая комиссия маркетплейсов, 
		отсутствие прямого контакта с клиентами, 
		невозможность собирать базу для повторных продаж (аксессуаров).

	Гипотеза: 
		создание собственного интернет-магазина позволит увеличить маржинальность и получить независимый канал сбыта.

1.2. Бизнес-цели (KPI)

	Номер: 			1 
	Цель: 			Проверить спрос на продукцию через собственный канал
	Метрика успеха: Получение минимум 10 реальных заказов в первый месяц после запуска
	Срок:			Первый месяц работы
		
	Номер: 			2
	Цель: 			Оценить удобство процесса заказа и оплаты для клиентов
	Метрика успеха: Доля успешно завершённых заказов (оплаченных и отправленных) от общего числа оформленных ≥ 60%
	Срок:			За 3 месяца

	Номер: 			3
	Цель: 			Создать основу для будущего масштабирования
	Метрика успеха: Сайт должен быть выполнен на технологиях, позволяющих добавить новые категории товаров без переписывания архитектуры
	Срок:			На этапе проектирования
		
	Номер: 			4
	Цель: 			Минимизировать операционные затраты на старте
	Метрика успеха: Администрирование сайта (обработка заказов) должно занимать у администратора не более 2 часов в день при 20 заказах в месяц
	Срок:			Сразу после запуска

1.3. Бизнес-ограничения (Out of the scope)

	- Нет интеграции с эквайрингом (оплата — только через СБП и банковские переводы по подтверждению менеджером).
	- Нет автоматической синхронизации с 1С или складскими системами.
	- Нет мобильного приложения — только адаптивный сайт.
	- Нет сложной CRM или системы лояльности на первом этапе.

1.4. Критерии успешности проекта (Acceptance Criteria)

	- Сайт запущен в открытом доступе по доменному имени.
	- Добавлены 3 модели кроватей-диванов с фотографиями и описаниями.
	- Форма заказа работает и отправляет данные администратору.
	- Администратор может менять цены и статусы заказов через интерфейс.
	- Первый заказ успешно обработан (полный цикл: заказ → звонок → оплата → отгрузка → отправка документов клиенту).

2.4. Бизнес-правила (ограничения для пользователей)

2.4.1. Авторизация

	Для оформления заказа пользователь вводит свой телефон и пароль — система автоматически создаёт или находит существующего клиента. 
	В качестве Логин применяется номер телефона.
	
2.4.2. Количество товаров

	На данном этапе только 3–5 моделей. Никакой пагинации.

2.4.3. Оплата 

	Не происходит на сайте — администратор связывается с клиентом по телефону и выставляет счёт.
	
2.4.4. Возвраты

	Оформляются администратором вручную, система фиксирует возврат и меняет статус заказа.
	После этого заказ считается закрытым и не влияет на статистику продаж.
	
3. Функциональные требования
   
3.1.Каталог

	Сайт должен отображать список из всех моделей кроватей-диванов. 
	Количество моделей не должно превышать 5 штук. 
	На данном этапе пагинация не предусматривается, 
		но архитектура должна позволять добавление пагинации или бесконечного скролла в будущем без переписывания основных модулей. 
	На текущем этапе все модели отображаются на одной странице.
	Страница каталога должна показывать: 
		название, 
		цену, 
		список фото (минимум 3 на модель), 
		подробное текстовое описание. 
	У каждой модели должен быть уникальный ЧПУ-адрес (глубокая ссылка) вида /product/sendai.

3.2. Форма заказа

	Отдельная страница с формой, содержащей поля: 
		Имя (обязательно), 
		Телефон (обязательно), 
		Адрес (текстовое поле, обязательно), 
		Комментарий (опционально). 
	После отправки форма должна отправлять данные на email администратора и сохранять в БД. 
	Пользователь должен иметь возможность перейти на форму заказа со страницы каталога по кнопке.

3.3. Управление заказами

	Администратор имеет доступ к списку всех заказов с возможностью 
		просмотра деталей, 
		изменения статуса (Новый → Подтверждён → Оплачен → Отправлен → Доставлен → Закрыт/Возврат), 
		добавления трек-номера, 
		прикрепления файлов (фото чеков) и отправки этих файлов на email клиента одной кнопкой.
	Система должна давать администратору возможность отвечать на сообщения пользователей через общий чат поддержки:
		администратор имеет доступ к отдельному разделу «Обращения», 
		где видит список всех сообщений от пользователей (не привязанных к конкретному заказу). 
		В этом разделе администратор может отвечать на сообщения в режиме инлайн-редактирования. 
		Отправка ответа происходит через систему уведомлений (на email пользователя).
	Система должна давать администратору возможность отвечать пользователю по вопросам конкретного заказа:
		в карточке каждого заказа должен быть предусмотрен блок для переписки с клиентом. 
		администратор может отправлять сообщения клиенту (на email) и видеть историю переписки,
		чтобы уточнять детали доставки, оплаты и возврата.
	Система должна требовать от пользователя авторизации через указание своего телефона и пароля при оформлении заказа. 
	Только авторизированный пользователь может создать заказ.
	Система должна давать администратору возможность 
		просматривать список вопросов от пользователей, в общем чате поддержки,  
		давать ответы пользователю на этой же странице в режиме редактирования инлайн, 
		иметь кнопку для отправки сообщений конкретному покупателю, 
		отображать статус заказа и ответ пользователя (инлайн чат).
	Система должна позволять администратору создавать возврат на заказ (изменять статус на «Возврат», фиксировать причину, сумму).
	Система не подразумевает эквайеринг. 
	Оплата заказа идёт через сторонние системы.

3.3.1. Процесс оформления возврата

	Возврат товара инициируется администратором вручную, когда заказ уже находится в статусе «Отправлен» или «Доставлен». 
	Алгоритм действий:
		Администратор выбирает строки заказа для возврата.
		Система показывает форму, где администратор вводит причину возврата.
		Проверяется длина текста причины (валидация). 
			При ошибке администратору показывается форма с уже введённым текстом и пояснением, что нужно исправить.
		После успешной валидации статус заказа меняется на «Возврат», причина сохраняется в БД.
		Если сохранение прошло успешно, клиенту отправляется уведомление по email.
		В случае сбоя почтового сервиса система логирует ошибку, а администратор уведомляет клиента по телефону.
		При ошибке БД транзакция откатывается, статус не меняется, администратору предлагается повторить попытку позже.
	
	UML вариант диаграммы действий (activity diagram) находится в Приложении А.

3.4. Управление каталогом

	Администратор может изменять 
		цену, 
		описание,
		фото любой модели. 
	Администратор может создавать новую модель (не через копирование существующей). 
	Архивация старых моделей не предусматривается. 
	Модели, выщедщие из продажи должны помечаться отдельным статусом и не показываться на странице каталога.
	В каталоге продаваемых моделей покупатель должен иметь возможность видеть только продаваемые модели.
	Если модель распродана, на странице каталога вместо кнопки «Заказать» отображается надпись «Распродано», 
		но карточка товара остаётся видимой (с отметкой). При желании администратор может скрыть модель полностью, 
		установив статус «Неактивна».

3.5. Статистика

	Администратор видит дашборд с метриками: 
		общее число заказов, 
		число заказов за сегодня/неделю/месяц, 
		сумма продаж за месяц, 
		количество заказов в статусе «Новый» и «Подтверждён».
	Графическое отображение (графики) не требуется. 
	Метрики отображаются только в виде цифр. 
	Выгрузки в Excel/CSV не требуется.

3.6. Уведомления

	При создании нового заказа система отправляет письмо администратору на указанный email. 
	Клиенту после оформления приходит письмо с копией заказа.

3.7. Дизайн-система

	Все страницы строятся на основе единого набора компонентов (UI-кит). 
	Это обеспечит единообразие при добавлении новых разделов в будущем.

4. Нефункциональные требования
   
4.1. Производительность

	Все страницы (кроме админки) загружаются 
		не дольше 2 секунд 
		при скорости интернета 10 Мбит/с 
		при одновременном количестве пользователей не более 50 человек.

4.2. Безопасность

	Вся админ-часть защищена паролем. 
	Сайт работает по протоколу HTTPS.
	Все формы должны быть защищены от CSRF-атак.
	Вход в админ-панель ограничивается по IP-адресам (опционально) и 
		имеет защиту от перебора пароля (не более 5 попыток за 15 минут).
	Все пользовательские данные экранируются для предотвращения XSS-атак.

4.3. Надёжность

	БД должна выдерживать до 10 000 заказов без деградации скорости.
	Система должна стабильно работать 
		при средней нагрузке в 50 RPS и 
		выдерживать пиковую нагрузку до 100 RPS

4.4. Удобство (Usability)

	Форма заказа должна быть доступна за 2 клика с главной страницы, 
		а кнопка «Заказать» видна без скролла на карточке товара.

4.5. Адаптивность и совместимость
	
	Сайт должен корректно отображаться на следующих устройствах:
		Десктопные экраны (ширина ≥ 1024px)
		Планшеты (768–1023px)
		Мобильные телефоны (≤ 767px)
	Поддерживаются последние версии браузеров: 
		Google Chrome, 
		Firefox, 
		Safari, 
		Edge. 
	Интерфейс должен быть удобен для сенсорного управления (крупные кнопки, отступы).

	@startuml
	|Система|
	start
	:Показать список заказов;
	:В одной строке заказ одной штуки товара, сумму и статус. Если за один раз было куплено несколько товаров, заказ разбивается на несколько строк списка;
	if (Статус заказа "Отправлен" или "Доставлен"?) then (Да)
	:Кнопка "Сделать возврат" активна;
	|Администратор|
	:В строке(строках) возвращаемого товара поставить крыжик;
	:Нажать кнопку "Сделать возврат";
	|Система|
	:Показать форму для заполнения возврата выбранного товара;
	repeat
	|Администратор|
	:Ввести причину возврата;
	|Система|
	:Проверить корректность причины на длину текста;
	if (Данные валидны?) then (Нет)
	|Система|
	:Показать форму с ошибкой и введённой причиной;
	|Администратор|
	:Исправить данные и повторить;
	:Переход к началу цикла;
	endif
	repeat while (Данные невалидны?) is (Да) not (Нет)
	|Система|
	:Изменить статус заказа на "Возврат";
	:Сохранить причину в БД;
	if (Сохранение в БД успешно?) then (Да)
	:Отправить письмо клиенту с уведомлением;
	if (Письмо отправлено успешно?) then (Да)
	:Показать список заказов с обновлёнными статусами;
